# שירות חיבור וסנכרון אשראי

## מה הושלם ומה עדיין דורש הפעלה

ממשק האפליקציה מתחבר לשירות HTTP נפרד עם Supabase Auth. השירות מחזיק חיבורים מוצפנים,
מריץ תהליך ספק אחד בכל פעם, מקבל קודי אימות מהמשתמש ומסנכרן כל 12 שעות.
השירות קולט עסקאות לתיבת האישור הקיימת; הוא אינו מאשר או מוחק תנועות כספיות אוטומטית.

הקוד נבדק מול ספקים מדומים, כולל זרימת UI של התחברות → OTP → הצלחה. לא הוזנו פרטים
פיננסיים אמיתיים. ההגדרות, HTTPS והמיגרציה הושלמו; נדרשת עדיין בדיקת ספק אמיתי.
ב־16.10.2026 הוקם ב־DigitalOcean שרת `finance-card-sync` בפרנקפורט, Ubuntu 24.04,
עם 2GB RAM, מעבד אחד ו־50GB דיסק, במחיר בסיס $12 לחודש ללא תוספות בתשלום.
תמונת `finance-card-sync:local` נבנתה עליו בהצלחה ובדיקת `tests/browser-smoke.mjs`
עברה עם מגבלת 1500MB וללא swap למכולה. זו בדיקת דף מלאכותי בלבד, לא התחברות לספק.
הבנייה הראשונית דרשה 4GB swap זמני לפתיחת ארכיון הדפדפן. לבניות חוזרות בשרת קטן
יש לספק זיכרון בנייה מספיק או לבנות את התמונה במכונה אחרת; מגבלת הריצה אינה מגבלת הבנייה.
השירות פעיל ב־`https://142.93.99.71` ומחזיר health תקין. הוגדרה תעודת IP חינמית של
Let's Encrypt וחידוש אוטומטי פעמיים ביום; בדיקת חידוש dry-run עברה. המפתח הייעודי
`finance_sync` נשמר רק בקובץ שרת בהרשאות 0600, והעותק הזמני להעברה נמחק.
מיגרציית תיבת הייבוא הוחלה ב־Supabase ונבדקו RLS והרשאות. בדיקת HEAD ללא קריאת
עסקאות החזירה 200; מקור זר נדחה ב־403 וטוקן חסר/לא תקין ב־401. המכולה healthy.
האפליקציה נפרסה ב־`https://finance-app-six-ivory.vercel.app` עם כתובת השירות.
הפריסה נעשתה באמצעות Vercel CLI. מאגר הקוד הוא `6leonid66-blip/finance_app`;
סודות, קובצי התחברות וצילומי מסך של ההקמה מוחרגים מהמאגר ומהפריסות.
20 בדיקות אוטומטיות, lint ובניית production עברו. התחברות אמיתית לספק ו־OTP אמיתי
עדיין לא נבדקו; אין להסיק מבדיקות התשתית שספק מסוים כבר סונכרן בהצלחה.

## שילוב עם Vercel

האפליקציה הקיימת נשארת ב־Vercel. המימוש הנוכחי משתמש בשירות Node מתמשך עם דיסק קבוע
ו־HTTPS, למשל בשרת Docker. זה אינו handler רגיל של Vercel Functions: בקשת ה־HTTP קצרה,
ואילו תהליך הדפדפן שממתין לקוד חי ברקע. התיעוד העדכני של Vercel מציע גם Daemons בבטא,
אך הם אינם מקבלים תעבורה נכנסת. שימוש בהם מחייב התאמה לתור פקודות ולאחסון משותף במקום
שרת ה־HTTP וה־SQLite המקומי במימוש הנוכחי. לא הוספנו הגדרות daemon לא בדוקות ל־vercel.json.

מקורות: [מגבלות Functions](https://vercel.com/docs/functions/limitations),
[Daemons](https://vercel.com/docs/daemons).

## פריסה של המימוש הנוכחי

1. במסד Supabase להריץ את המיגרציות הקיימות ולאחריהן
   `supabase/migrations/202610160900_card_sync_inbox.sql`. לבדוק תחילה בסביבת staging.
2. בשרת לשמור קובץ `sync-worker/.env` לפי `.env.server.example`:
   - `APP_ORIGIN`: כתובת האפליקציה המדויקת, לדוגמה `https://app.example.com`, ללא לוכסן סופי.
   - `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: גישה שרתית למסד האפליקציה.
   - `SYNC_ENCRYPTION_KEY`: 32 בתים אקראיים ב־base64, שמורים במנהל סודות של השרת.
   - `SYNC_DATA_DIR=/data`, `HOST=0.0.0.0`, `PORT=8787` בפריסת Docker.
3. הפקת מפתח, ישירות במסוף פרטי של השרת: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.
   אין להדביק את התוצאה בצ׳אט, לשמור ב־Git או להשתמש בתחילית `VITE_`.
4. מתוך תיקיית `sync-worker`: `docker compose up --build -d`. נשמר volume קבוע של חיבורים.
   תמונת הבנייה מתקינה Camoufox מראש. תהליכי סנכרון לא מורידים דפדפן בזמן התחברות המשתמש.
5. להגדיר reverse proxy עם תעודת HTTPS תקינה אל `127.0.0.1:8787`. הפורט קשור ל־loopback
   בקובץ compose; אין לחשוף אותו ישירות לאינטרנט. גוף בקשה מוגבל ל־16KB בשירות.
6. ב־Vercel להוסיף **רק** `VITE_CARD_SYNC_URL=https://sync.example.com` ולבצע redeploy.
   כתובת זו ציבורית. מפתח ההצפנה ומפתח service-role נשארים בשירות הפרטי בלבד.
7. לאחר התחברות לאפליקציה: אשראי → חיבור חברת אשראי → בחירת חברה והזנת פרטי כניסה.
   להפעיל עם משתמש בדיקה וכרטיס אחד תחילה, ולהשוות את הסכומים לדוח חברת האשראי.

השירות משתמש ב־service-role כדי לקלוט עסקאות בלי לשמור סיסמת Supabase או refresh token של
המשתמש. כל בקשת משתמש מאומתת באמצעות `auth.getUser`, החיבור משויך למשתמש המאומת בלבד,
וחברות בבית נבדקת לפני התחברות לספק ושוב לפני קליטת התוצאה. חשיפה של מפתח service-role
מסוכנת ולכן הוא לא מועבר לתהליכי הדפדפן או למשתמשים. אל תפעילו מספר replicas עם ה־SQLite הזה.

## פיתוח מקומי

נדרש Node 24 ומעלה. `npm ci` מתקין את התלויות. יש לאפשר את בניית `better-sqlite3`
ואת סקריפט התאימות של חבילת הסנכרון; בסביבת פיתוח שבה scripts חסומים ניתן לבצע
`npm rebuild better-sqlite3 --ignore-scripts=false` אחרי סקירת החבילה, ואז להריץ את
`node node_modules/@sergienko4/israeli-bank-scrapers/scripts/patch-playwright-core.mjs`.
`npm run browser:install` מתקין את Camoufox (הורדה משמעותית, כ־1.3GB לפי תיעוד הספק).
`npm run serve` קורא את `.env` ומפעיל את השירות.

למחשב המקומי: `APP_ORIGIN=http://127.0.0.1:5173`, `HOST=127.0.0.1`,
`SYNC_DATA_DIR=./private-data`, ובאפליקציה `VITE_CARD_SYNC_URL=http://127.0.0.1:8787`.
אין להפנות אפליקציית HTTPS לשירות HTTP. המסך לא מאפשר הזנת פרטים כשהשירות לא מוגדר או לא זמין.

המחבר הישן בשורת הפקודה נשמר לתאימות: `.env.cli.example`, `npm start`, `npm run watch`.
הוא אינו מסלול ה־OTP מהממשק ואין להשתמש בהגדרותיו במקום הגדרות השרת.

## התנהגות, פרטיות וגבולות

- נתמכות MAX, כאל, ישראכרט ו־Amex. שדות ההתחברות נבדקים מול metadata של החבילה הנעולה.
  כל חיבור שייך למשתמש, לבית ולחברת אשראי. כל כרטיסי אותה התחברות נקלטים יחד.
- פרטי הכניסה נשלחים ישירות מהאפליקציה לשירות המוגדר ומשם לספק. שמירה נעשית רק לאחר
  הסכמה מפורשת. הם מוצפנים ב־AES-256-GCM עם nonce אקראי ו־AAD הקושר אותם לבעלים ולחיבור.
  API הקריאה מחזיר metadata בלבד. אין שימוש ב־localStorage לשמירת סיסמאות או קודי אימות.
- קוד אימות נשמר בזיכרון בלבד, קשור ל־challenge אקראי ולמשתמש, ונצרך פעם אחת. התוקף הוא
  שלוש דקות, עד שלוש בקשות קוד בריצה. אם ספק אינו קורא ל־OTP callback הנתמך, אין מנגנון
  שעוקף זאת; תוצג שגיאת ספק. אין תמיכה בפתרון CAPTCHA אוטומטי.
- משך ריצה מוגבל לעשר דקות. תהליכי הדפדפן מבודדים בתהליכי משנה, בלי מפתחות שרת ועם
  פלט גולמי מושתק. עצירה מסיימת את עץ התהליכים ומנסה להסיר את תיקיית הריצה הזמנית.
- כל עוד השירות פעיל, סנכרון מוצלח מתוזמן שוב בעוד 12 שעות. חסימת חשבון, סיסמה שגויה,
  OTP שפג וכל כשל אחר עוצרים ניסיונות אוטומטיים עד התערבות המשתמש. אתחול מחדש מפסיק
  את הריצות שהיו פעילות ומציג צורך בניסיון חדש; הוא אינו משחזר קוד אימות או תהליך דפדפן.
- השהיה מבטלת ריצה פעילה ותזמון אך שומרת פרטי חיבור מוצפנים. ניתוק מוחק את רשומת החיבור
  ומפסיק ריצות; עסקאות שכבר נקלטו נשארות. כתיבה שכבר נשלחה למסד עשויה להסתיים במהלך הניתוק.
  גיבויי volume/WAL כפופים למדיניות שימור של מפעיל השרת; מחיקת רשומה אינה מחיקת גיבויים.
- יש לגבות את volume ואת מפתח ההצפנה בנפרד. אין החלפה אוטומטית של מפתח: שינוי המפתח
  ללא הצפנה מחדש של הרשומות ימנע פענוח ויחייב חיבור מחדש. הגישה לשרת ולגיבויים חייבת להיות מוגבלת.
- ההגבלה הראשונית היא 100 חיבורים בשירות וריצה אחת בכל פעם. יש הגבלת בקשות ופעולות לכל משתמש.
  שירות גדול יותר דורש תור משותף, מנעולים מבוזרים, מכסות וניטור תפעולי.
- משתמש שעזב את הבית יכול עדיין למחוק את החיבור הפרטי שלו. ריצות לא ייבאו עסקאות לאחר
  שלילת חברות שהתגלתה בבדיקה. נדרשת מדיניות מנהל למחיקת רשומות של משתמשי Auth שנמחקו.

## נכונות עסקאות

רק עסקאות סופיות עם מזהה יציב ומטבע חיוב שקלי נקלטות. מועד הרישום הוא `processedDate`
לפי שעון ישראל. חיובים שליליים נרשמים כהוצאה; זיכויים חיוביים כהכנסה. עסקאות ממתינות או
ללא מזהה מדווחות במונים ולא נקלטות. מטבע חיוב חסר/זר או פורמט לא תקין מכשילים את הקליטה.

מניעת כפילות מבוססת על חברה, חשבון מקור, מזהה, מספר תשלום ותאריך חיוב. שינוי מזהה/תאריך
בספק עלול ליצור רשומה חדשה; תיקון סכום תחת אותו מזהה אינו דורס עסקה קיימת. יש לאשר ולבדוק
מול הדוח. שני משתמשים המייבאים אותו כרטיס אינם מאוחדים: יש להקצות בעלים אחד לכרטיס משותף.
אין לייבא שוב חיוב מרוכז מהבנק כהוצאה לצד פירוט הכרטיס. החזר נרשם כהכנסה, לא כהפחתה
מהוצאות קטגוריית המקור. תיבת האישורים מציעה קישור לתנועות שכבר קיימות באותו סכום וחודש.

## בדיקות ואבטחת תלויות

`npm test` בתיקייה זו בודק הצפנה וזיהוי שינוי ciphertext, שדות ספק, תאימות `adm-zip`,
הרשאות, CORS, הסכמה, הפרדת משתמשים, OTP חד־פעמי ותוקף, עצירת ניסיונות לאחר כשל,
תזמון, השהיה, ניתוק ובדיקת חברות חוזרת. `npm test` בשורש בודק חישובים, קליטה ואת SQL.

ב־16.10.2026 `npm audit` בשורש ובתיקיית השירות החזיר אפס חולשות ידועות. הוחלפה
`israeli-bank-scrapers@6.12.2` ב־`@sergienko4/israeli-bank-scrapers@8.8.0` ונוסף override
ממוקד ל־`adm-zip@0.6.1`. החבילה ההורית עדיין דורשת טווח ישן; נוספה בדיקת תאימות לארכיון.
תוצאת audit אינה כוללת את מערכת ההפעלה או את הדפדפן שבתמונה ואינה תחליף לסקירת אבטחה.
יש לעדכן ולסרוק את התמונה לאחר בנייתה ולבדוק מול כל ספק לפני פתיחה לקהל.
